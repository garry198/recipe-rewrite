# AGENTS.md — правила для ИИ-воркера (Antigravity)

Ты пишешь код проекта **recipe-rewrite**. Задания ставит и принимает **Claude** (координатор/ревьюер),
владелец проекта — человек, который запускает скрипт и отправляет Claude твои diff'ы. Отвечай по-русски, коротко.

## Цикл работы
1. Прочитай `tasks/rNN.md` (самое свежее невыполненное), `docs/STATE.md`, `docs/CONTRACTS.md`.
2. Работай **только в ветке `worker/rNN`**, коммить локально; в `main` не коммить и не пушить.
3. Один коммит на подзадачу: `rNN.M: суть`.
4. В конце: `.\tools\make_review_pack.ps1 rNN`, заполни `reviews\rNN\worker_notes.md`.
5. Остановись. Не бери следующее задание сам, жди новое от Claude. Слияние делает владелец командой `.\tools\merge_branch.ps1 worker/rNN` после приёмки Claude; если приёмка требует правок, дополняй ту же ветку подзадачами `rNN.1`, `rNN.2`… и пересобирай пакет.

## Жёсткие правила
- Не трогай то, что не названо в задании. Минимальный diff, без массового переформатирования и переименований.
- Секреты: `.env`, ключи, пароли, данные подключения никогда не читать в вывод, не коммитить, не вставлять в diff.
- БД: только `SELECT` через MCP `mysql_ro`. Любая запись в БД — только сам скрипт при запуске владельцем.
  Никаких ALTER/UPDATE/INSERT/DELETE, даже «временно».
- Каждое исправление поведения = новый тест в `tests/test_regressions.py` (на реальный случай, ID рецепта в имени).
  Перед сдачей: `python tests\test_regressions.py` → «все тесты пройдены», `python -m py_compile rewr-transl.py checks.py`.
- Версии кэша: меняешь логику `checks.py` → поднять `CHECKS_VERSION`; логику масштабирования → `SCALE_VERSION`;
  единицы/перевод → `UNITS_VERSION`. Смена версии = сброс кэша = платные вызовы API, упомяни это в заметке.
- Промпты версионируются именем файла (`prompts/..._vN_M.txt`). Старые версии не править и не удалять, только добавлять новые.
- Не запускай скрипт с боевым API-ключом и не делай вызовы Gemini, если в задании нет явного «можно запускать».
  Для проверки используй тесты и `DRY_RUN=true`.
- Не придумывай данные: нет информации (структура БД, формат другого пайплайна) → пиши вопрос в `worker_notes.md`,
  а не угадывай.
- Если задание противоречит этим правилам или самому себе — остановись и напиши вопрос, не выбирай сам.

## Как сдавать изменения
- **(а) Ветка:** одна задача — одна ветка `worker/rNN` от `main`; в `main` не коммитить и не сливать.
- **(б) Пакет ревью:** после работы запускать `.\tools\make_review_pack.ps1 rNN`; итог — `reviews/rNN/` (`diff.patch`, `tests.txt`, `worker_notes.md`, `stat.txt`, `commits.txt`, `compile.txt`, при конфликте — `merge_resolution.patch`).
- **(в) `worker_notes.md`:** только итог, без пересказа процесса, по структуре из `tools/make_review_pack.ps1` («Что изменено», «Версии», «Тесты», «Проверка на эталоне (было/стало)», «Запись в БД», «Что не сделано / отклонения», «Вопросы к Claude», «Как проверить»).
- **(г) Кодировка:** логи и любой длинный вывод — в UTF-8 (`Out-File -Encoding utf8`); в Windows PowerShell 5.1 не использовать `>` и `Tee-Object` без кодировки.
- **(д) Секреты:** ключи API и значения секретов нигде не писать, только `key_fp`.
- **(е) Документация:** правки `AGENTS.md`, `docs/*` коммитить сразу, не оставлять незакоммиченными.
- **(ж) Конфликты слияния:** конфликт (в т.ч. при `git merge main` в свою ветку) не разрешать молча — сохранить разрешение в `reviews/rNN/merge_resolution.patch` (`git diff` после разрешения) и описать в `worker_notes.md`.
- **(з) Игнорируемые папки:** папки из `.gitignore` (`inbox/`, `backups/`, `reviews/*`) git не создаёт — создавать вручную (`New-Item -ItemType Directory -Force`).

## Формат заметки
`worker_notes.md` заполняется по шаблону из `tools/make_review_pack.ps1` (кратко, только итог, без пересказа diff и процесса).
